# ADR 0004：流式进程与工作区文件协议

- 状态：Accepted
- 日期：2026-10-02
- 关联：ADR 0001、ADR 0002、ADR 0003；taifeng ADR 0108（按组杀）、ADR 0113（`WorkspaceFS`）
- 参照：asyncio `StreamWriter` / `StreamReader` 的接口与惯例（Python 标准库，PSF 许可证）

## 背景

ADR 0003 定下第 1 版线协议时，进程只能一次性收输出，标准输入固定接 `/dev/null`；taifeng 的 `WorkspaceFS` 也还没有落地，`DaemonWorkspace` 只有本仓自己的接口。之后内核补上了两个对接口：

- `StreamingCommandProcess`：内核 `McpStdioClient` 经执行器起 MCP server，要能持续写标准输入、按行读输出；
- `WorkspaceFS`（taifeng ADR 0113）：文件类工具经它读写工作区，命令在沙盒里改的文件，`file_read` 读到的也得是沙盒里的那份。

本 ADR 记录为接上这两个对接口所做的决定：线协议第 2 版、宿主侧的流式进程、`DaemonWorkspace` 的边界与错误语义、整文件写入的原子替换及其代价。第 2 版在本包首次发布之前定稿。

## 决策

1. **线协议第 2 版：进程可以接标准输入。**
   - `process/start` 新增可选布尔参数 `stdin`，为真时标准输入接管道，否则仍接 `/dev/null`。
   - `process/write` 向标准输入写一段数据（单次最多 16 MiB）。守护进程每个进程一把写锁，并发到达的写按到达顺序整块写入；写缓冲回落到水位线以下（`drain`）才回复，回复就是背压信号。宿主每次写都等到响应再发下一次，这类请求**不受请求超时约束**（进程不读标准输入时守护进程可以合法地一直不回），时限由调用方经取消施加。
   - `process/closeStdin` 是**发起式**关闭，立即回复 `{}`；缓冲里没进管道的数据在后台继续写，与本机管道一致。
   - 宿主侧 `StreamingRemoteProcess` 把这些包成 `stdin` / `stdout` / `stderr` 三个流。某一路**未读字节超过上限时杀掉进程、让这一路的读取方报错，不丢弃也不交出截断的数据**——MCP 报文截断后无法再对齐，宁可失败。收到不是合法 base64 的输出块同样按失败处理。取消 `drain` 不丢在途的那一块：已发出的块照常送达，没发的留在缓冲里，下一次 `drain` 接着发，字节流按顺序恰好送达一次。
   - 一次性收输出的 `RemoteProcess` 移到 `daemon/process.py`，`StreamingRemoteProcess` 是它的子类。
   - **v2 在首次发布之前定稿**：越界错误码 `-32024`（见决策 6）属于 v2。守护进程源码随包分发、连接时注入，宿主与守护进程总是同一版本；守护进程只接受与自己相同的版本，v1 宿主与 v2 守护进程握手即失败，不互通。

2. **按组杀与 taifeng ADR 0108 对齐。** shell 先退出、它派生的子进程还占着管道时，主进程已经有退出码，但组里还有成员要杀，所以不能凭 `returncode` 判定「已经结束」。本机后端用 `_collected` 标志：只有 `communicate()` 收完两路输出之后 `kill` 才是空操作，此前一律按组发 `SIGKILL`。守护进程先收完两路输出、等主进程退出，再把进程移出进程表，然后才发 `process/exited`；表里还在的进程，`process/kill` 一律按组杀。

3. **本机流式进程的单行读取上限 16 MiB。** asyncio 子进程流默认 64 KiB，经本机执行器起的 MCP 连接器单条响应超过它时，内核的 `readline` 抛 `ValueError`、读循环崩掉。`spawn_group` 传 `limit=STREAM_LIMIT_BYTES`，取值与守护进程执行器每路未读字节的默认上限 `DEFAULT_MAX_BUFFER_BYTES` 对齐：远端流式进程的一行也得整行放进那个缓冲才读得出，两类后端能交出的单行一样长。由测试守护两边一致。

4. **`DaemonWorkspace` 实现 `taifeng.WorkspaceFS`。** `root` 取握手信息里守护进程上报的根目录，缺失或不是规范的绝对路径就抛 `SandboxProtocolError`，不猜默认值。`metadata` / `list_directory` 直接返回内核的 `WorkspaceFileInfo` / `WorkspaceEntry`，删掉本仓自有的 `FileMetadata` / `DirectoryEntry`，不留兼容层（尚未发布）。内核五个文件类工具的 `workspace=` 可以直接接它。这闭环了 ADR 0002「`WorkspaceFS` 未落地」那条后果。

5. **文件方法的边界分两层，真实边界在守护进程。**

   | 层 | 怎么校验 | 作用 |
   | --- | --- | --- |
   | 客户端 `DaemonWorkspace.resolve` | 同步、纯路径计算：相对路径拼到 `root`，`..` 按字面折叠，开头多个 `/` 规整成一个，**不跟随符号链接**；越界抛 `WorkspacePathError` | 给内核工具产出规范路径（权限 target 与回显）；每个方法发请求前自己先调一次，不依赖调用方 |
   | 守护进程 `PathGuard` | `realpath` 解析符号链接后仍须在根目录之内，否则 `-32024`；之后对**真实路径**操作 | 真正的边界：根内指向根外的链接、`..`、同前缀的兄弟目录都在这里拦下 |

   这一表补充 ADR 0003 决策 5 的边界表里「宿主经文件方法能碰什么」一行。字面 `resolve` 有这些后果：
   - 权限 target 与结果回显是字面路径。根内有符号链接时，它与实际读写的物理文件不一致——这与内核 `LocalWorkspaceFS`（`resolve` 跟随链接、返回真实路径）不同。
   - 按路径写的权限规则可以被根内链接绕开：规则拦 `secrets/*`，根内的 `link -> secrets` 让 `link/x` 的 target 不落在规则里。需要按路径做强约束的宿主，不要在工作区里留指向受限目录的链接，或在执行环境层面隔离。
   - `..` 是字面语义，与 shell 不同：`a` 是指向别处的链接时，`a/../b` 在这里就是根下的 `b`，shell 里却是链接目标的父目录下的 `b`。
   - 守护进程对真实路径操作，所以 `fs/remove` 一个符号链接删掉的是链接目标、不是链接本身（与内核 `LocalWorkspaceFS` 一致）。

6. **错误码与异常映射。** 越界从 `-32020` 中分出来，单独用 `-32024`；`-32020` 只表示操作系统拒绝访问、删除根目录本身，或 root 守护进程改不回原属主（见决策 7）。`DaemonWorkspace` 的映射：

   | 线协议 | 宿主侧异常 |
   | --- | --- |
   | `-32021` | `FileNotFoundError` |
   | `-32024` | `taifeng.WorkspacePathError`（`PermissionError` 的子类） |
   | `-32020` | `PermissionError` |
   | 其他错误码 | `SandboxRemoteError`（`OSError` 子类，带 `code`） |
   | 连接断开；响应字段缺失或类型不对 | `SandboxProtocolError` |

   响应字段缺失或类型不对一律算协议错误，不拿默认值顶上。路径里有 NUL、布尔参数给了非布尔值，守护进程回 `-32602`。

7. **`fs/writeFile` 的非追加写入是原子替换。** 守护进程在目标所在目录写一个 `.tmp-` 开头的临时文件，先写完数据，再在它的 fd 上设权限与属主，最后 `os.replace` 到目标；任何一步失败都删掉临时文件、目标不动。读者只会看到旧内容或新内容。
   - 权限：覆盖保持原文件的权限位 `& 0o777`（可执行位不丢，setuid / setgid / sticky 不保留）；新建按守护进程**启动时**读到的 umask，与直接 `open` 写入一致。
   - 属主：守护进程以 root 运行时保持原属主（与临时文件属主相同时不调 `fchown`，没有 `CAP_CHOWN` 的 root 照常覆盖自己的文件；原属主是别人而改不回时整次写入报 `-32020`，不悄悄改掉属主）；非 root 改不了属主，覆盖后属主是守护进程的用户。新建文件属主不动。
   - 超过单次上限 16 MiB 的写入由宿主分段：第一段原子替换，之后逐段追加，**整体不是原子的**。线协议没有 rename，不为此加方法。同理，超过 16 MiB 的读取按 `offset` 分段，**不是快照**：两段之间文件被改，拼出来的内容可能新旧混杂。
   - 往根目录本身写返回 `-32022`（否则临时文件会建到根目录的父目录、即根外）；删除根目录本身返回 `-32020`。
   - `fs/getMetadata` 遇到 `NotADirectoryError`（路径中间某一段是文件）返回 `{"exists": false}`，与 `FileNotFoundError` 一样。

8. **原子替换接受这些代价：**
   - 父目录必须可写：只读目录里的可写文件，原来能原地写，现在会被拒绝。
   - 断开硬链接：替换后目标是新 inode。附带安全收益——原来经根内的硬链接截断写，改写的是根外那个 inode（`realpath` 看不穿硬链接）。
   - 非 root 守护进程覆盖后，属主变为守护进程的用户。
   - 只读文件（如 `0444`）可以被覆盖：改名只要求父目录可写；原来 `open(..., "wb")` 会被拒绝。
   - 目标是单文件 bind mount 时，改名到挂载点得到 `EBUSY`（`-32022`）。
   - 并发的列目录、`glob` 能短暂看到 `.tmp-*`；守护进程在建临时文件与改名之间被杀，会残留 `.tmp-*`。
   - 不 `fsync`：保证的是读者看到的原子性，不是掉电后的持久性。

9. **已知限制：父目录的检查与使用之间有竞争窗口（TOCTOU）。** `PathGuard` 先按 `realpath` 校验，之后才打开或改名；这期间如果有别的进程把路径中的某一级目录换成指向根外的链接，操作会落到根外。
   - **威胁模型**：容器里守护进程与模型执行的命令同 uid、同挂载命名空间。能抢赢这个竞争的模型，本来就能直接用 shell 写那些路径；根目录约束守的是工具层的权限 target 与审计记录的一致性，不是提权边界。所以第 2 版不做加固。
   - **必须加固的情形**：守护进程的权限高于它执行的命令（例如守护进程是 root、命令降权运行），或文件方法开放给沙盒里命令之外的主体（例如另一个用户经宿主驱动文件方法，而沙盒里跑着不受信任的进程）。
   - **加固方案要点（dirfd）**：逐级以 `O_DIRECTORY | O_NOFOLLOW` 打开父目录并核验其真实路径仍在根内；在父目录 fd 上以 `O_CREAT | O_EXCL | O_NOFOLLOW` 建临时文件（读取同样经 `dir_fd` + `O_NOFOLLOW` 打开）；`fchmod` / `fchown` 都对 fd 做；最后 `os.replace(tmp, name, src_dir_fd=dfd, dst_dir_fd=dfd)`。

## 否决的方案

- **越界与无权共用 `-32020`、靠错误消息区分**：消息是给人看的文字，不是契约；客户端无法据此可靠地还原成 `WorkspacePathError`。
- **客户端 `resolve` 先发请求问守护进程真实路径**：`resolve` 在内核协议里是同步的，而且每次多一次往返；真实边界本来就由守护进程守。
- **用 `mkstemp` 的 0600 直接作为目标权限**：模型改一个脚本后可执行位会丢，挂载到宿主的工作区里 uid 不同的宿主用户读不到。
- **为大文件原子写入加 `fs/rename`**：现有工具用不到，内核 `WorkspaceFS` 协议也没有这个成员；需要时再加可选方法。
- **流式进程超限时丢弃输出并计数**（`RemoteProcess` 的做法）：MCP 报文截断后无法对齐，静默丢弃会让读取方把残缺数据当成完整的。

## 后果

ADR 只增不改，以下旧条目的正文不动，只在 [决策索引](README.md) 里标注：

- **取代 ADR 0003 决策 1** 的方法清单：第 2 版新增 `process/write`、`process/closeStdin` 与 `-32024`，当前清单以 [线协议](../architecture/protocol.md) 为准。
- **部分取代 ADR 0003 决策 8**：「超出部分丢弃并计数」只对一次性收输出的 `RemoteProcess` 成立；流式进程超限是杀进程并报错（决策 1）。
- **取代 ADR 0003 后果第 2 条**：本机后端与守护进程执行器都支持流式进程（`CommandSpec.stdin=True` 时返回 `StreamingCommandProcess`）。
- **补充 ADR 0003 决策 5** 的边界表（决策 5）与**决策 7** 的按组杀（决策 2）。
- **闭环 ADR 0001 决策 1** 中「`WorkspaceFS` 对接口落地后同步接入」，以及 **ADR 0002 决策 1**「后者待 taifeng 落地」与**后果第 2 条**。
- 守护进程 `server.py` 到 759 行，接近 800 行的硬上限。再加功能之前，要先决定怎样在保持「单文件注入」的前提下拆分。
