# ADR 0002：容器与远端后端走「沙盒内守护进程」范式

- 状态：Accepted
- 日期：2026-09-29
- 参照：codex `exec-server`、`exec-server-protocol`、`file-system`（Apache-2.0）

## 背景

容器、K8s Pod、虚拟机这类后端和宿主不在同一个进程空间，常常也不在同一台机器上。如果每个后端各自实现「执行命令 + 读写文件 + 出网策略」，N 个后端就有 N 套语义，而且很容易出现错位：命令在沙盒里执行，文件却在宿主机上读写。taifeng 当前的文件类工具直接读写本机 `root_dir`，就是这个问题。

codex 的解法是 `exec-server`：在执行环境里跑一个小的 JSON-RPC 守护进程，统一提供进程执行、文件访问和网络策略，宿主侧只需要一个客户端。

## 决策

1. **分三层**：
   - **宿主侧客户端**：同时实现 taifeng 的 `CommandExecutor` 与 `WorkspaceFS`（后者待 taifeng 落地）。
   - **线协议**：本仓自己定义并做版本管理，设计参照 codex `exec-server-protocol`。
   - **沙盒内守护进程**：执行命令、访问文件、执行出网策略。
2. **环境提供者只管拉起环境**：docker、k8s 等后端只负责「拉起环境 + 在里面启动守护进程」，共用同一个客户端与守护进程。
3. **自带守护进程的云沙盒直接适配 SDK**：E2B、Daytona 等不强行塞入本仓守护进程。
4. **本机 OS 级隔离不需要守护进程**：bwrap、Landlock、seatbelt 直接包装本机进程启动；隔离策略参照 codex `sandboxing`，复用处注明出处。

## 否决的方案

- **直接用 codex `exec-server` 作沙盒内守护进程**：那是 codex 的内部协议，迭代快、不承诺对外稳定，依赖它等于把兼容性交给别人的发版节奏。只借鉴设计，协议自有。
- **每个后端各自实现执行与文件访问**：语义分叉，出网策略也无法统一。

## 后果

- 守护进程是本仓唯一需要跨平台分发的组件，分发形态（单文件可执行 / 容器镜像）在第一个容器后端落地时决定。
- taifeng 的 `WorkspaceFS` 落地之前，容器后端只能靠挂载目录保证文件视图一致；远端后端要等它落地。
